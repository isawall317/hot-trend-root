## Step 2: 竞品深度调研

### A. 传统云成本监控（成熟、拥挤、企业向）

| 竞品 | 产品形态 | 定价 | 用户量/评价 | 核心功能 | 不足之处 |
|------|----------|------|------------|----------|----------|
| **AWS Cost Anomaly Detection** | 官方内置 | 免费 | 所有 AWS 用户 | ML 异常检测、日级评估 | **正是本次事件里失效的那个**——日级评估抓不住日内飙升；阈值高时小幅持续突增会漏 |
| **Vantage** | Web SaaS | 免费档 ≤$2.5k/月云支出；付费 ~$300/月起 | FinOps 团队为主 | 成本报告、预测、异常检测、标签治理、多云 | 起步价高，独立开发者/小项目用不起；面向 FinOps 团队非个人 |
| **CloudZero** | Web SaaS | 企业定制（按管理支出抽成），门槛 $50k+/月支出 | 中大型企业 | 单位成本经济学、K8s 成本分摊、异常检测 | 门槛极高；AWS 为主；与个人开发者无关 |
| **阿里云成本管家 / 费用中心** | 官方内置 | 免费 | 国内所有阿里云用户 | 预算告警（50/80/100%）、异常消费检测、成本分析 | 通用、企业向；告警粒度粗；只覆盖阿里云自身；**不覆盖 AI API 花销** |
| **Datadog Cloud Cost / CloudHealth** | Web SaaS | 企业定价 | 中大型企业 | 多云成本可视化、监控集成 | 重型企业栈，独立开发者不会上 |

**A 类结论**: 传统云成本监控赛道**已饱和**，且全是企业向。个人/小团队 + 多云 + AI API 这一段是空缺——但云厂商官方免费工具"够用但不靠谱"（AWS 事件证明了），独立工具要靠"早 30 分钟 + 跨厂商 + AI API"差异化。

### B. LLM API 花销监控（更新、但形态偏重）

| 竞品 | 产品形态 | 定价（未验证） | 核心功能 | 不足之处 |
|------|----------|---------------|----------|----------|
| **Helicone** | LLM 网关/代理 + 仪表盘 | 有免费档（未核实额度） | 调用日志、成本统计、延迟、异常 | **需把流量代理过去**——独立开发者要改 SDK 调用方式，摩擦大；偏 observability 不是"止损" |
| **Portkey** | LLM 网关 | 有付费档（未核实） | 多 provider 路由、预算告警、缓存 | 同样是 gateway 形态，要接 SDK；面向团队 |
| **Langfuse** | 开源 LLM observability | 自部署免费 / 云付费 | trace、成本、评估 | observability 不是 cost guard；需接 SDK |
| **各 AI 厂商自带 usage 面板** | 官方 | 免费 | 用量统计 | 各家各管各，无统一告警；DeepSeek/OpenAI/Claude 三家要分别盯；**无异常爆炸检测** |

**B 类结论（关键）**: LLM 花销监控这条线**没有"轻量、不改 SDK、纯告警"的独立工具**。现有方案要么是重 gateway（要代理流量），要么是厂商各管各。这恰是信号 1 真正的差异化缺口——**不是"云账单"，而是"AI API 花销 guard"**。

## Step 4: MVP 范围定义（经验证后**收窄重构**）

> 验证后最重要的修正：MVP 不应是"云账单防护"（赛道饱和、企业向、AWS 官方免费），而应收窄到 **"AI API 花销 guard"**——这是真正的空缺，且与 Frank 画像（自己用多家 AI API + Claude Code 跑长任务）直接重合，还和发现报告信号 2（Agent 长任务监控）天然合并。

### 重定位后的 MVP：**AI API 花销 Guard**

#### 必须做（核心价值）
1. **接 3 家 AI 厂商 usage/billing API**（OpenAI / Anthropic / DeepSeek）拉取当日花销 — 理由：这是"独立于厂商的第二道闸"的根本，且这三家覆盖 Frank 自身用量
2. **日基线 + 异常飙升检测**（当日花销 vs 过去 7 日同时段均值，超 3σ 推送）— 理由：AWS 事件的核心痛点是"异常飙升时告警滞后/失效"
3. **飞书/微信推送**（异常即推，附"哪个 key / 哪个模型"归因）— 理由：Frank 日常用飞书，推送渠道要贴近他
4. **Claude Code session 日志的 token 烧速读取**（读取本地 .jsonl，显示当前 session 实时花销）— 理由：把信号 1 和信号 2 合并，Claude Code 是 Frank 自己在用的，自己就是首个用户

#### 可以不做（等验证后再加）
1. 自动止损（断 key / 限流）— 理由：误杀风险高，且需厂商 API 支持，先只报警
2. 多云账单（AWS/阿里云）— 理由：赛道饱和、官方免费，不是差异化点；AI API 才是
3. Web 仪表盘 — 理由：先做 CLI + 推送，验证有人付费再做 UI
4. 团队/多账号 — 理由：先单用户验证

#### 技术方案
- **形态**: CLI 工具（`aiguard`）+ 定时任务（cron/launchd），先本地跑
- **技术栈**: Python（复用本仓库 tools/collector 的 uv 环境）或 Node；读取 Claude Code `~/.claude/projects/*/*.jsonl`
- **AI 可替代**: ~70%——API 对接、日志解析、异常检测基线都是 AI 可生成的样板代码；人要做的是厂商 API 鉴权细节 + 推送链路稳定性
- **预计工时**: AI 辅助下 ~12-16 小时（2 个周末）

#### 上线渠道
- **主渠道**: 开源到 GitHub + npm/pipx 安装（降低信任门槛，因为要读 AI API key）
- **冷启动**: 
  - Frank 公众号 7000 粉发一篇"AWS 收我 17 亿美元账单？我自己写了个 AI 花销 guard"——故事性强、痛点具体
  - V2EX / 即刻 / 少数派 发布
  - Claude Code 中文社区（即刻、微信群）

## Step 5: Go/No-Go 决策

## 决策: 🟡 观望 → 收窄后转 🟢 Go（条件性）

### 支撑信号
- ✅ 痛点真实且有具体事件佐证（AWS 故障 + 厂商告警失效）
- ✅ 验证后找到了真正的差异化缺口：**LLM 花销监控赛道缺"轻量、不改 SDK、纯告警"工具**（Helicone/Portkey 要代理流量，摩擦大）
- ✅ Frank 自己就是目标用户（用多家 AI API + Claude Code 跑长任务），能自己做首个用户
- ✅ MVP 工时可控（~12-16h），符合"5-10h/周 + 睡后收入"画像
- ✅ 可与信号 2（Agent 长任务监控）天然合并，共享技术栈

### 风险信号
- ⚠️ 搜索热度未验证（5118/百度指数没访问到）——需求规模无数据支撑，只能靠 Frank 自身感受 + AWS 事件间接推断
- ⚠️ Helicone/Portkey 定价未核实——可能已有更便宜的轻量档位，需手动核实
- ⚠️ 厂商 usage API 各家成熟度不同（DeepSeek 尤其不确定是否有 usage API）——技术可行性需 spike
- ⚠️ 开源 CLI 难直接变现（睡后收入弱）——可能需后续加托管 SaaS 层才有付费点
- ⚠️ "AI API 花销"是否够痛？云账单爆炸是低频事件，用户可能"出事才想起"——留存是隐患

### 如果 Go
1. **下一步动作**: 先做 **2 小时技术 spike**——核实 OpenAI/Anthropic/DeepSeek 三家 usage/billing API 是否可拉取当日花销（DeepSeek 是最大不确定点）。spike 通过 → 开干；不通过 → 收窄到 OpenAI+Anthropic 两家或改读 Claude Code 日志估算
2. **同时做**: Frank 公众号发一篇痛点文（AWS 事件 + 自己被 AI API 账单惊到的故事），24h 看互动 → 这是最便宜的种子用户验证
3. **预计 MVP 上线时间**: 2 周内（一个周末写核心 + 一个周末打磨推送 + 发布）
4. **成功标准**: 
   - 上线 2 周内 GitHub star > 100（冷启动基线）
   - 公众号文章互动 > 平时 1.5x（验证痛点共鸣）
   - 找到 3 个真实使用反馈（评论/issue）

### 如果 No-Go（备选）
- 原因：DeepSeek 无 usage API 且 Frank 自己用得不痛 → MVP 失去首个用户
- 存档：本报告存入 `data/archive/`，未来 AI API 计费标准化后重启

## 总结

验证修正了原信号的两个偏差：
1. **赛道偏差**：原信号瞄准"云账单"，但该赛道被 AWS 官方 + Vantage + CloudZero + 阿里云官方饱和，独立工具无优势。**真正的缺口是 AI API 花销监控的轻量形态**。
2. **形态偏差**：原信号想做多云 billing，但 Helicone/Portkey 已占"重 gateway"位。**轻量 CLI + 纯告警 + 读 Claude Code 日志**是没人占的窄缝。

修正后 Go 的条件是 **2 小时技术 spike 通过**（三家 AI 厂商 usage API 可拉取）。建议 Frank 现在就做两件事：跑 spike + 发痛点公众号文。两者成本都极低，结果直接决定 Go/No-Go。
