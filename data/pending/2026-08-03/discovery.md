## 🔥 信号 1: 云账单异常"爆炸"防护工具

**证据热点** (1 条，但痛点极度具体):
- [InfoQ] AWS 计费系统故障：用户收到数万亿美元账单预估，自家成本告警却未能阻止问题扩大 — "一个平时每月不足 5 美元的账户，预估账单竟显示为 17 亿美元"

**底层需求**: 云用户（尤其中小团队/个人开发者）最怕的不是贵，而是"账单突然爆炸时厂商告警滞后/失效"。AWS 这次事件里，成本告警**没能阻止问题扩大**——说明现有厂商侧监控对"异常飙升"不可靠。用户需要一个独立于云厂商的"第二道闸"。

**目标用户**: 中小 SaaS 团队、独立开发者、用多个云/AI API 的 side project 玩家（与 Frank 的"小软件睡后收入"画像高度契合，自己就是用户）

**AI 解决方案**:
- AI 能做：异常检测基线学习（区分"正常增长"vs"异常爆炸"）、根因归因（哪个服务/region/API key 突增）、告警文案与止损建议
- 人要做：多云 billing API 对接、止损动作（断 key / 限流）的权限与安全设计

**MVP 形态**: 接 AWS + 阿里云 billing/CloudWatch API，5 分钟级拉取消费曲线，偏离日基线 3σ 即推送（飞书/微信），一键生成"可疑资源 Top 10"报告。先不做自动止损，只做"早 30 分钟报警"。

**可行性**: 7/10 — billing API 成熟、痛点真实、MVP 范围可控；扣分项是多云差异 + 厂商官方在补这块（窗口期）

**变现**: SaaS ¥29/月/账号，或按"保护的云支出"抽 1%；国内版主打阿里云/腾讯云 + AI API（OpenAI/Claude/DeepSeek）花销监控——后者正是当前 AI 应用团队的真实焦虑

**风险**:
- 云厂商自己会做（AWS Cost Anomaly Detection 已有但明显不够好——这恰是机会）
- 多云 API 差异大，工程量随云数量线性增长 → MVP 先单云（阿里云或 AWS）打透
- 止损动作有误杀风险（先只报警不自动止损）

## 🔥 信号 2: AI Agent 长任务运行监控 Dashboard

**证据热点** (3 条，方向一致):
- [InfoQ] 阿里 Qwen3.8 发布：自主编程 16 天搓出一个 Hermes Agent
- [InfoQ] OpenAI "Astra" 新模型曝光：重点在多个智能体长时间协同、解决高难度问题
- [机器之心] Karpathy 两小时 10 美元做了一个《指环王》3D 游戏（文字→应用）

**底层需求**: Agent 越来越能"长时间自主跑"（16 天编程、多智能体协同、几小时生成游戏）。但用户在中途**完全不知道**：它跑到哪一步了、卡在哪、烧了多少 token、是不是在原地打转。现有 agent（Claude Code/Cline/Cursor）日志是流式文本，没有"运行态可视化"。这是一个随 agent 自主时长增长而放大的新缺口。

**目标用户**: vibe coding 开发者、用 Claude Code/Cline 跑长任务的人、agent infra 团队

**AI 解决方案**:
- AI 能做：从 agent 原始日志中抽取"意图-动作-结果"三元组、检测"卡死循环"（同一步重复 N 次）、token 烧速预测、自然语言进度摘要
- 人要做：解析各 agent 的日志格式、设计 dashboard UI、异常推送

**MVP 形态**: 一个本地跑的 dashboard，读取 Claude Code / Cline 的 session 日志（jsonl），实时显示：当前任务、步骤数、token 消耗曲线、最近 5 步动作、卡死检测。先单 agent（Claude Code），不做多 agent 编排。

**可行性**: 7/10 — 日志格式已知（本仓库就在用 Claude Code）、痛点是新出现的且随 agent 自主时长放大、MVP 可基于现有日志不依赖厂商；扣分项是市场还早期、付费意愿待验证

**变现**: 开源核心 + Pro（多 agent / 云同步 / 团队共享）¥49/月；或走 GitHub Sponsors 起步验证

**风险**:
- 各厂商日志格式不统一、且会变（Claude Code 改版就需跟）
- 厂商自己会做运行态 UI（Cursor 已有部分）→ 须主打"跨厂商 + 卡死检测"差异化
- 市场早期，用户教育成本高 → 先在 Claude Code 中文社区冷启

## 🔥 信号 3: 商超"断货王"监控 + 到货提醒

**证据热点** (1 条):
- [36氪] "散装山姆"挤满打工人，9.9 小绿瓶成断货王，单季爆卖 544 亿 — "线上频繁卖断货，门店贴出限购通知"

**底层需求**: 沃尔玛/山姆的 9.9 元爆款（小绿瓶牛奶等）反复断货、限购，打工人想买却买不到。现有电商"到货提醒"在商超自营小程序里要么没有、要么慢。需求是"抢断货王的最早到货窗口"。

**目标用户**: 一二线城市打工人、薅羊毛群体、家庭采购主力（小红书/微信群已有自发"代购"生态，说明付费/付费意愿存在）

**AI 解决方案**:
- AI 能做：多门店库存页定时抓取、到货模式识别（哪个店几点补货）、用户偏好匹配
- 人要做：门店库存接口/页面抓取的合规与稳定性、推送链路

**MVP 形态**: 微信小程序，用户订阅"某商品 + 某门店"，后台定时（每 10 分钟）查库存，到货即微信模板消息推送。先单城市（如上海）单连锁（沃尔玛）打透。

**可行性**: 6/10 — 技术简单、痛点真实、有自发代购生态验证需求；扣分项多：商超页面结构易变/反爬、单一渠道依赖、商超自己会优化到货提醒

**变现**: 小程序会员 ¥9.9/月（薅羊毛群体愿付）；或导购佣金（如果接商超联盟）

**风险**:
- 商超库存接口/页面变更频繁，维护成本高
- 商超官方自己做（风险最大）→ 须靠"跨连锁 + 多城市 + 比价"建立壁垒，但这又放大工程量
- 反爬/合规边界 → 只抓公开库存页、不做破解登录
